# NAS Photo TV 1.2.5 发布说明

- 发布日期：2026-11-17
- 版本：`1.2.5`（versionCode 11）
- 安装包：`NasPhotoTV-1.2.5-release.apk`（**正式签名**，推荐）/ `NasPhotoTV-1.2.5-debug.apk`（debug 签名）

## 反馈问题

> 对于 4K 60 帧视频播放，竖屏视频支持比较差。

## 排查结论

竖屏素材本身能解码，问题出在**呈现方式**与**两个数据字段读错**。逐条如下。

### 1. 竖屏画面只占屏幕中间一条（主因）

2160×3840 的竖拍素材在 1080p 电视上按比例完整显示时只有 **607px 宽**，左右各留 **656px 死黑** —— 观感上像是「播放器不支持竖屏」。

### 2. 缓冲预算写死，高码率素材周期性卡顿

旧实现把目标缓冲写死成 48 MB、最短缓冲 8 秒：

- 20 Mbps 的 1080p：8 秒只要 20 MB，48 MB 够放 19 秒 —— 够用；
- **130 Mbps 的 4K 60fps：8 秒要 130 MB，远超 48 MB 上限**。字节数一到顶就停止加载，于是每次只缓冲到约 3 秒就开播，播完立刻重新缓冲 —— 表现就是「4K 60 帧每隔几秒卡一下」。

竖拍 4K60 素材码率通常 **120–150 Mbps**（比横拍更高），所以这个问题在竖屏素材上更明显。

### 3. 视频时长恒为 0（连带多处失效）

fnOS 的 `gallery` 响应里时长字段叫 **`mediaDuration`（单位：秒）**，而旧代码读的是 `durationMs` / `duration`，两个都不存在。后果：

- 卡片上的时长角标**完全不显示**；
- 按码率规划缓冲算不出码率（`size / duration` 除零），只能走兜底预算；
- 信息面板拿不到可靠时长。

### 4. 自动连播会把图片丢给播放器（播完即卡死）

调用方传入的是「当天/当相册」的**图片+视频混排**列表，自动连播的下一条很可能是图片。旧版把一张 PNG 截图交给 ExoPlayer，得到 `0:00 / 0:00` 的永久黑屏 —— 用户看到的是「播完这个视频就卡死」。

## 修复内容

1. **竖屏三档画面适配**（设置页「视频播放 · 竖屏画面」，或播放中按 `MENU` 循环，选择会持久化）：

   | 模式 | 效果 |
   |---|---|
   | `自动填充`（默认） | 画面完整居中，左右用**该视频自己的封面放大压暗**填充 —— 不丢画面又不留死黑 |
   | `铺满屏幕` | 按高度铺满、裁掉左右（会切掉画面上下） |
   | `完整画面` | 传统 letterbox，左右纯黑 |

2. **缓冲预算按码率自适应**：用 `文件大小 / 时长` 估算码率，以 `8 秒 × 码率 × 1.25` 算预算并夹在 32–64 MB，再把时长目标收敛到这份预算装得下的范围 —— 保证 `maxBufferMs` 永远撞不到字节上限，缓冲不撞墙就不会周期性重新缓冲。码率未知时退回旧参数。

3. **修正时长字段**：按 `mediaDuration`（秒）解析，兼容 `durationMs`（毫秒）与 `duration`，并用 24 小时阈值兜住极老的毫秒口径。

4. **播放器只播视频**：进入时先过滤出视频再编号，`第 n / m 个` 的 m 现在是**视频数**；从原列表第 N 项进入时正确映射下标。

5. **竖屏识别加兜底**：NAS 元数据缺失宽高时，退到解码器回报的真实尺寸（media3 已把旋转折算进宽高）。

## 新增：外网中转 / 反向代理地址支持

此前地址栏只接受「主机 + 端口」，协议写死为 HTTPS、路径写死为根路径，因此带子路径的中转地址即使写进配置也登录失败。本版把地址拆成 **scheme / host / port / basePath** 四段并全程贯通：

- 「地址」栏可直接填完整 URL：`http://relay.example.com:8080/nas`、`https://relay.example.com/nas/`；也兼容原来的纯 IP / 域名。
- API、图片、访问码校验与 WebSocket 全部挂到子路径下（`/nas/p/api/v1/...`、`/nas/websocket?type=main`）；`http` 下 WebSocket 自动降级为 `ws`。
- 旧配置里写在 `nas_host` 的完整 URL 启动时会**自动拆分迁移**，无需重填。
- 切换地址 / 协议 / 子路径会正确作废媒体缓存与客厅展示授权。

> 反向代理需把子路径前缀剥掉再转发到飞牛 Web 服务（如 `location /nas/ { proxy_pass https://NAS_IP:5667/; }`）。`authx` 签名针对飞牛内部 `/p/api/...` 原路径，前缀不参与签名。

## 关于「自动转码 / 降级选流」的调研结论（2026-11-17）

针对「4K 60 帧播不了能否自动转码或降码率」的想法，做了实测调研，**结论是这条路走不通**，记录如下以免重复踩坑：

- **相册 API 只给原片**：`/p/api/v1/stream/v/{id}` 实测无论加 `quality=720p`、`quality=480p`、`resolution=1280x720`、`transcode=1`、`format=hls`、`profile=high` 哪一种参数，返回的都是**同一份 134 MB 原片 MP4**（`Content-Type: video/mp4`，字节数完全不变）。参数被直接忽略。
- **没有对外转码端点**：`/p/api/v1/transcode/{id}`、`/p/api/v1/video/quality/{id}`、`getSupportedQuality`、`/v/api/v1/media/*` 等全部返回 `501 The route you are looking for is not found` 或 `404`。
- **转码引擎存在但不对外开放**：飞牛 `mediasrv` 二进制里确实有完整的 HLS 转码链路（`HlsTranscoder`、`generate_master_m3u8`、`get_supported_quality`、`forceH264`、Intel QSV/VAAPI 硬解等符号，本机还有 Intel UHD 核显），但它通过 `/v` 路径 + **playLink 机制**只服务于飞牛官方 Web/桌面客户端（依赖浏览器登录 cookie 会话）。第三方 OAuth 应用拿不到 playLink，因此无法请求转码流。
- **Web 播放器并非 HLS**：飞牛 Web 端的 `VideoPlayer` 是 xgplayer 直接播放原片，前端资源里没有任何 m3u8/hls.js 引用 —— 浏览器端靠自身软解 HEVC，而不是服务端转码。

**因此**：在不引入「模拟浏览器登录拿 cookie」这类脆弱且违反 OAuth 契约的做法的前提下，本客户端**无法**实现服务端转码或降级选流。若后续飞牛官方开放转码 API，可在 `FnOsMediaRepository` 的 `videoUrl` 解析处接入多码率流。

### 替代方案：解码能力预检 + 友好降级（已实现）

既然改不了片源，就在播放端做两件事：

1. **解码能力预检** — `ui/video/VideoCapabilityProbe.kt` 用 Android 官方 `MediaCodecList` 枚举设备的视频解码器，检查 H.265/H.264/AV1/VP9 是否支持、是否支持 **10bit**（HEVC Main10 等 profile）、最大解码分辨率。播放失败时用它结合视频规格生成针对性诊断（例如「4K 10bit 原片超出这台电视的解码能力」），而不是笼统一句「解码失败」。
   - 预检只用于**解释原因**，不拦截播放：软解、厂商私有解码器、ExoPlayer 的 decoder fallback 都可能让「看起来解不了」的片子实际能播，真实结果仍以 ExoPlayer 为准。
2. **封面降级界面** — 解码/网络失败时不再显示黑屏 + 一行小字，而是用该视频自己的封面铺满做底（压暗 78%），叠加一张信息卡：标题 → 规格（`3840x2160 · 原片直连（飞牛未提供转码流）`）→ 针对性原因 → 明确操作（按「下一曲」跳过，并显示当前第几个/共几个）。用户一眼知道是哪条视频、为什么不行、下一步做什么。

**模拟器实测**（`DJI_20260929150141_0258_D.MP4`，3840×2160 59.94fps HEVC Main10 10bit）：
- 降级界面正确显示四项信息，文案与 logcat 真实错误 `NO_EXCEEDS_CAPABILITIES` / `hvc1.2.4.H150` / `10bit Luma` 一致；
- 按 `MEDIA_SKIP_FORWARD` 成功从第 1 个切到第 2 个，第 2 个同类素材同样正确降级 —— 完整链路通过。

## 已知局限

- 本机模拟器与部分电视盒子**无法解码 4K 60fps HEVC 10bit** 素材（`NO_EXCEEDS_CAPABILITIES`），这类素材仍会显示「这个视频无法播放」+ 原因。本次修复的是**可解码素材**的画面呈现与缓冲，**没有**自动转码或降级选流（原因见上节调研结论）。
- 「竖屏画面」只改变显示方式，不改变码流本身。
- 4K 60fps 高码率素材的流畅度仍受电视解码能力与网口带宽限制（README §8 记录：100 Mbps 网口下 129 Mbps 原片必然间歇缓冲）。
